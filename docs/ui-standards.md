# UI standards

How StartDGX looks and behaves. **The shared rules are in the devkit: [scripts/devkit/docs/ui-standards.md](../scripts/devkit/docs/ui-standards.md)** (principles, windows, moving and resizing, remembered state, controls, words, notifications). Read it first. This file holds only where StartDGX differs from it or adds to it, and the [decision log](#decision-log).

**Both files are the source of truth for the UI.** A change that makes a design decision neither covers, or goes against one, updates the file it concerns in the same change and adds a line to the decision log. A UI change without a matching update is not finished.

The kit's fifth principle names this app's tool: the QML never runs ssh, the engine or a terminal itself; it asks `bin/startdgx`, and only through `DgxService.qml` and `HostPoller.qml`. Its only other processes are local: `notify-send` (with `--` and the body escaped) and the `mkdir` of the bar icon's status folder (see the decision log).

## Differences from the shared rules

- **No settings window of the app's own yet** (a machine and a model each have one: see [Settings windows](#settings-windows)), so no first run, no Window page and no *Remember size* / *Remember position* switches.
- **The manager is an ordinary window** (a Quickshell `FloatingWindow`, titled StartDGX), not the kit's full-screen overlay with a scrim: the compositor moves, resizes, tiles and closes it like any application, so there is no drag strip, resize grip or scrim of our own (Esc and the ✕ still close it, and so does the compositor's close key). Cards still float over the manager inside the window, veiled behind. The kit's overlay rules (dismiss by a click on the scrim, move by the top strip) don't apply to the manager. Where it opens and how big is the compositor's business, which is why nothing is remembered; the default is 640 by 580.
- **Size and position are not remembered** across a shell restart: the compositor decides where the manager opens, and it opens at its default size after a restart (see the decision
- **Cards float over the manager; the gear's settings windows are the family's** (`SettingsWindow.qml`, copied from StartAppImage, pages left and settings right, applied at once, 760 wide, no resize or move yet): Add machine, a machine's uninstall and forget cards, model picker, Add recipe card and Find on Hugging Face card, a model's remove card, a recipe's run card, and **settings windows** (the gear on a machine's or a model's row; see [Settings windows](#settings-windows)). They follow the stacking rules (the manager stays behind under a 35% veil, Esc and a click outside close only the card), but they are centred on the manager, sized to their content (560 wide), and neither move nor resize. While a card is open it takes the pointer's hover as well as its clicks, so nothing behind it shows a tooltip over it.

- **Header.** The chip mark, the name, the count line in sentence case (only the parts that need you, a failure or a machine not answering, are red; `DgxModel.summaryParts`), and look again (refresh). There is no "Machines" label: the machines say what they are. On a narrow manager the count line takes a second line rather than lose its end, which is the part that matters (failed, not answering).
- **A machine.** A dot on its name's line (accent when it answers, red when it doesn't, muted before its first answer), its name, its SSH target and what it is (`DgxModel.hostLine`), and a **gear** (its settings window). Under the name: "Asking the machine…", "No models set up yet", or why it doesn't answer and when it last did (`offlineText`); that its engine has an update; that it needs its root setup. A name too long for the row is cut before it reaches the gear. Under it, on a machine that answers, its **memory bar** (`MemoryBar.qml`, `DgxModel.hostMemory`): the machine's `ram_total_gib` as the track and one segment per running model (and one for a model that is loading, with what the machine holds beyond the running ones, "Name loading" under the bar), in the accent stepped toward the foreground (so it follows the theme), with "28 of 122 GiB in use" (or "Nothing loaded · 122 GiB free") under it and a model's name and size on a segment's hover. It is the design's one bold thing: a Spark runs out of memory, and that is what fails a start. A machine that doesn't answer keeps its last known models, dimmed and without buttons.
- **A model.** A flat row, not a card: a hairline between rows, a lift on hover and the accent border under the keyboard cursor. Its maker's mark, its name (plain, not bold, so the machine's bold name stays the higher level; whole, with the endpoint, on hover) and, when it is shared on the tailnet, the Tailscale mark. **When the row is 600 wide or more** the facts are columns that line up down the machine: status (dot and word), context ("256K"), memory it holds or last held ("31 GiB") and where its files are ("NVMe", "USB", "NVMe + USB"; only on a machine with a model store; `DgxModel.modelColumns`, `locationShort`). **Narrower**, a status dot and one line under the name (`DgxModel.modelLine`) as before. Then **gear** (its settings window: share, logs, context size, where its files are), **Remove…** (a muted trash; **Cancel the setup…**, an ✕, while it downloads) and **Start/Stop**. The gear and the trash show only on the row under the pointer or the cursor; Start and Stop are always there. The line says, most telling first: what the model is doing (`DgxModel.modelState`: Running, Loading, Stopping, Removing, Cancelling, Waiting to download, Downloading, Moving to USB, Failed, the reason it doesn't fit, Stopped), its context and the memory it took, where its files are (only on a machine with a model store) and *Shared*. When the row is too narrow the line wraps onto a second line between facts, never under the buttons; what a third line would hold is cut and shown whole on hover. The three buttons keep their places on every row: one with nothing to do now (no removal while a model is being removed, no Start while it downloads) is hidden, not taken away, so the others never move under the pointer. A model that doesn't fit has its play button greyed out; the line says why, and so does the button on hover. Under it, a meter (`DgxModel.meter`): none while it runs (its memory is its column and a segment of the machine's bar); progress while it loads, stops or is removed, against how long that took last time; the download while it is set up (an empty Waiting bar until it begins). A failure's reason is a red line of its own, wrapped, which opens the logs.
- **Start and stop** show once their command runs on the machine ("pending"), and the machine's next answer after the command replaces it. So does a **removal**: the row says Removing (Cancelling, for a setup) until the model is gone. Each machine runs two commands at once: a start (which returns only once its model has loaded), and a stop, set up or removal beside it, each with its queue (`DgxModel.submit`). A command waiting its turn leaves the row as the machine says, with "· stop queued" (start, removal) after it; a start waiting its turn can be taken back with Stop.
- **A machine that needs its root setup.** When Set up fails because the engine says the machine needs Podman set up as root first (`DgxModel.setupNeeded`), the machine says so in red and gets an **Install…** link: `install --replace-engine` in a terminal, which backs up an engine startdgx didn't install and does the root setup. The footer only points at it.
- **Add model…** is the last row of a machine that answers (a cursor row like the others); it opens the machine's model picker.
- **Footer.** **Add machine…** on the left, the latest message (six seconds, red for an error) or "Esc to close" on the right (`FooterNote.qml`, in the cards that show messages too): a long message takes a second line, and one cut even then is whole on hover. A setup's message drops the engine's pointers to the agents panel and journalctl (`DgxModel.actionNotice`): the row follows the setup.
- **Keyboard.** The keys are `DgxModel.keyAction`, so a key and a button cannot disagree (a machine that isn't answering has no Start, Stop or Logs either way, and a model that doesn't fit is never started); each button's tooltip names its key. No single key destroys anything: `d`, `u` and `f` open a card that asks. A held Enter, `s`, `t`, `d` or `f` acts once (its auto-repeat is ignored, in the cards too).

| Key | Does |
|---|---|
| Up, Down, `k`, `j` | Move the cursor over machines and models |
| Enter, `s` | Start or stop the model under the cursor (on Add model…: open the picker) |

| Esc | Close |

## Settings windows

The gear on a machine's row or a model's (`g`) opens its settings window (`SettingsCard.qml` around `SettingsWindow.qml`); `DgxModel.hostPages` and `modelPages` build the pages, `hostChange` and `modelChange` say what a click asks. The window's title is the machine's or the model's name, whole: a long one takes up to three lines.

| Window | Page | What is on it |
|---|---|---|
| A machine's | General | **Update…** or **Install…** when the engine has an update or the machine needs its root setup; **Logs** |
| | Storage | The **model store**: a choice among the usable disks (a long path is cut in the middle, whole on hover) or a folder of your own. Dimmed while models are on the store; the note that says why stays at full strength |
| | Machine | **Uninstall…** and **Forget…**: both open a card that asks, so neither is red |
| A model's | General | **Share on my tailnet**, **Logs** |
| | Context | The context sizes the recipe has measured that fit this machine, one segment each with the memory it needs ("256K · 54 GiB"), the one in use lit. A click on another size restarts the model with it (`use --ctx`); a click on the lit one does nothing. The page stays, dimmed, while the model restarts, and is dimmed while the machine doesn't answer. A size fits as the engine says it does: within memory, not drafted, and an estimated one only once confirmed. A context the recipe measured more than once is one segment, with the numbers of the variant the engine runs (`DgxModel.contextChoices`, the engine's `pick_variant`: the one that needs the most memory and still fits). **One size is not a choice**: when the only size that fits is the one in use, the page says the size, what it needs and that there is nothing to choose, with no segment to click. Sizes that don't fit are listed under "Not offered", with why; a model running a size that is no longer offered is told which, and keeps its segments |
| | Storage | Where the files are and **Move to USB / NVMe / Free NVMe space** (only on a machine with a model store) |

The footer's line is red when it is an error (a path that won't do, a change the machine refused), and takes a second line when long.

## Buttons

- **A row's action is a bordered `Button`** (Set up in the picker, Add and Install… in Add machine, Draft recipe and With an agent… in Find), and so are a footer's actions on the left (Look again, Add machine…). Icon-only on a manager row, with a tooltip that names its key.
- **A card's answer is a pill** (`SettingsPill`) at the bottom right: the quiet way out first (Cancel, Keep it, Not now), then the act, accent-filled (`primary`) or red (`danger`) when it destroys something. A settings window's actions are pills too.
- **A text link** (`TextLink`) is for the quiet extras of a list row (Variants, Remove, Confirm, Measure… in Add recipe) and a failure's reason.
- **Opt-ins on a card** (uninstall, Find's show/hide) are `SwitchRow.qml`: the label and what it does, with the family's round switch (`RoundSwitch.qml`) on the right, as in a settings window. There is one switch look.

## Add machine

Lists `startdgx discover --json` (it installs nothing and changes nothing on the machines; its ssh saves the host key of a machine it has never seen, in `~/.ssh/known_hosts`): each machine of the tailnet with its target and what it can do (`DgxModel.peerOffer`). A DGX Spark with startdgx's engine has **Add**, which adds it at once and marks it Added; one without an engine has **Install…**, which opens the install in a terminal (sudo asks there) and closes the window; one with an engine startdgx didn't install has both, and says that Install… backs that engine up first (`install --replace-engine`; uninstall puts it back). A machine that isn't a Spark, or doesn't answer, says so, dimmed (a machine that wants a password says to run `ssh-copy-id`). **User on the machines** is the ssh user discover asks as (empty: this machine's); Enter there, or **Look again**, asks the tailnet again as that user. Up/Down, Enter, `r`, Esc.

## Add model

A machine's model picker: every recipe of its catalog (`startdgx list HOST`), sorted by `DgxModel.recipeOffers`: the engine's recommendation first (marked *recommended*, its own `best`), then what the machine can run and doesn't have, what it has (*On this machine*) or is setting up, and what it can't run, dimmed, with the engine's reason. Each shows its maker's mark, the memory it takes, its context and speed on this machine class (`recipeFacts`) and its summary. **Set up** (Enter) runs `use --detach`, closes the card and puts the cursor on the new row, which shows at once as *Waiting to download* (`withSetups`) until the machine lists it, then follows the download through the status poll, then loads. A failure (exit code non-zero) takes the row away again and puts the CLI's last stderr line in the footer. **Look again** (`r`) reads the catalog again. **Add recipe…** (`e`) opens the Add recipe card. A user recipe wears a *yours* mark, and one whose numbers aren't measured says so and has **Measure…** (`pickerMeasureCtx`: the Measure card at the row's context, or Add recipe… when the row names none, as for a recipe no variant of which fits, which the engine lists without a source) (*estimated*, *drafted, not yet fitting*); a drafted recipe is dimmed, can't be set up, and says why. A recipe of yours that isn't set up has a trash icon that takes it off the machine's list (`recipe remove`, no card: only the recipe goes, its file stays here; the engine refuses while a model uses it and its words show under the list). Every row has a **gear** (`recipeSettings`, `DgxModel.recipePages`): the settings window of the family with *Contexts* and *General* pages. A recipe of yours lists each context with its source and **Measure…** (the confirmation card), **Confirm** for estimated numbers, **Add a context size** (32K to 256K, those it lacks; `recipe context`: a drafted variant with the biggest one's numbers as placeholders, written back through the engine's `recipe add`), **Remove a context size** (`recipe context --remove`; not the only one), *Fix with an agent* (`launch fix`, below) and *Remove recipe* (not while a model is set up from it); a curated recipe's window only shows. Repo, revision and license aren't shown: the panel doesn't read the recipe's text. Up/Down, Enter, `r`, `e`, Esc.

## Find more models

The model picker's **Find more models…** (`f`) opens one card with two sources, pills under its heading: **TensorFold** (the default) and **Hugging Face**. Both are read from this computer and add a model the same way: **Add** writes a recipe for it and puts it on the machine. On a TensorFold entry that has a memory estimate the add also confirms that estimate (ADR 0001, amended), so the row says **Added · memory estimated** with **Set up…** (the Recipe run card, showing only the download and what is loaded) and a quiet optional **Measure…**; a Hugging Face add, or an entry with no estimate, is **Added, not measured yet** with **Measure…** first, because nothing stands behind its numbers. The row says where its model stands on the machine (the machine's recipe list, read when the card opens and after an add). **Measure…** opens the Recipe run card (download size and what happens, then **Download and measure**), and after that it is a model like the others. **TensorFold** lists what tensorfold.dev publishes for one DGX Spark (`tensorfold list --json`, saved each time the card opens, so what is new or changed since the last visit is marked for this one); a row's **Customize** opens the three choices tensorfold.dev offers for that model, as pills with the defaults picked: **Context**, **Requests at once** and **Input** (text, or text + images). They become the recipe's variant context, its `--parallel` and its `--vision` flags (`tensorfold draft --context --parallel --input`; the engine has no video input, so video turns the vision tower on too); the memory figure stays TensorFold's estimate for its defaults, and Measure… finds the real numbers. Once a model is on the machine, its row says if TensorFold has moved on since (`tensorfold list --host`, from the record `tensorfold draft --host` keeps of the commit and choices it gave that machine): **Added, not measured · update available** with **Update** (a draft is replaced at once), **Added · update available** where the recipe was measured (the button turns into **Discard its measurement and update** and needs a second click, since `--replace` discards the measurement), and **On this machine · update available: remove the model first** where a model is set up from it. An update gives the machine the choices it had. An entry that can't be added yet (a format the engine's runtime isn't built for) is not a row: one line says how many, and **Show** lists them with the reason. Its memory figures are TensorFold's estimates and never a fit (ADR 0001). **Hugging Face** is the search below.

### The Hugging Face source

The model picker's **Find on Hugging Face…** (`f` there; IPC `findModel HOST [QUERY]`, `scripts/dev find HOST [QUERY]`) opens a card with a query field (Enter or **Search** runs `startdgx hf search --json`, on this computer: no host is asked, and Esc drops the typed query before it closes the card), one row per repo and a toggle. A row (`DgxModel.hfRowText`, `hfMemoryLine`) has the repo, then parameters, license (or "license unknown") and the base model, then the memory line as two plain facts: "weights 15.4 GiB; this host has 128 GiB" (the host's `ram_total_gib`, rounded; "weights size unknown" when the repo lists none). An abliterated or uncensored repo wears its label beside its name, in the foreground colour (accent is for the one thing to do and the selected state, so no label, warning or success line uses it). **Show/Hide abliterated and uncensored (N)** (`hfToggleText`) is on by default and shown only when a row is labelled; hiding touches no other row. A search that found nothing says so apart from one that did not run (the CLI's message, in red: offline, rate limited). Each row has **Add** (it was **Draft recipe**): one action that runs `startdgx recipe draft --host HOST --json REPO` (the host makes an id clash refuse before a file is written), then the Add recipe path (`recipe add`, validate first) with the file it wrote. The card shows the step, then the draft's warnings in the foreground colour, each led by "Warning:" (a restrictive, unknown or unreadable license) and, on failure, the clash or each validation error on its own row (the Add recipe card's rows); on success it says the recipe is on the machine as drafted, not yet fitting, which the model picker shows (`recipeMarks`, `DRAFTED_TEXT`). The buttons dim while any recipe write runs. The label has no ellipsis because it acts at once. `recipe draft` also has the host's engine validate its file, removes a draft that fails, and replaces a draft startdgx wrote and nobody edited, so a failed try can be repeated at once; a clash, or a file the person edited, is shown without the CLI's `--id` advice (`draftErrorText`), since the card has no id field: delete that file to draft again.

Each row also has **With an agent…** (ellipsis: it opens a terminal and asks you there). It runs `startdgx launch author HOST REPO` (`authorLaunch`, which refuses what is not OWNER/NAME) and nothing comes back to the card. Its tooltip (`authorHint`) says an agent finishes the recipe and asks before any download or measuring run; the agent command is the CLI's `agent_command` setting.

## Add recipe

A machine's card for adding a **user recipe**: a `.toml` you wrote, on this computer, in the **curated recipe**'s format. It takes a path (Esc drops the typed path first, then closes the card; the path is only handed to `startdgx recipe`, which reads the file, so there is no file dialog). **Add** (Enter) validates first with `recipe validate --json` and adds with `recipe add --json` only when nothing is wrong; **Check only** validates and changes nothing. Each error the engine finds is a row of its own (the first eight, then "and N more"); a machine that doesn't answer, or a file that can't be read, is one red line instead (the CLI exits 0 for a rejection, since the machine answered, and non-zero for the rest, so the card can tell them apart). The recipe's id is the file's name without `.toml`, which is what the engine does too.

Under the field, **your recipes on this machine** (`recipe list --json`, the rows with `user`): each with its id and marks, and **Remove**, which asks the engine (`recipe remove`) and shows its message in red when a model set up from the recipe is there, naming the model. Removing needs no card to ask first: only the recipe goes, and its file is still on this computer. Add, Remove, Confirm and a measure are writes, run one at a time and never ended by closing the card; the card's questions (validate, the list, the variants, a dry run) are Queries.

**Variants** (a link on each recipe) lists every variant of the recipe (`DgxModel.variantRows`: two at one context are two rows) with its source (`startdgx variants`, which reads the machine's own recipes and yours). A drafted variant has **Measure…**; an estimated one has **Confirm** (`recipe confirm`: it then counts as fitting) and **Measure…**; a measured one has neither.

## Recipe run

A recipe of yours downloads what it names and runs it, so the engine wants `--yes` for both a **measure** and a **setup**, and the panel sends it only from this card. **Measure…** (a variant) and **Set up…** (the picker's button on a user recipe) open it: it asks the machine what that would do (`recipe measure HOST ID --ctx N` without `--yes`, which changes nothing; for a setup the recipe's own context) and shows the engine's lines, the download first. Only **Download and measure** / **Download and set up** (or Enter, once the lines are shown) goes ahead; **Not now**, Esc or a click outside close it and nothing happens. A machine that can't say leaves the pill off. A measure takes minutes, holds the engine's lock and restarts a model that runs there, so it is a write nothing ends, with a message when it is done; a setup follows the model's own row. Setting up a curated recipe has no card, as before.

A **variant**'s **source** says where its numbers come from: *measured* (the default, and every curated recipe's), *estimated*, or *drafted*. A recipe without `user` or `source` is curated and measured. A drafted variant never counts as fitting, in the picker (the recipe is dimmed and can't be set up) and on the Context page of the model's settings (its size is not offered, with why); an estimated one is marked as such, and counts as fitting only after **Confirm** in the Add recipe card's variants list (`recipe confirm`; the variant then reads *you confirmed it*, and measuring replaces its numbers with real ones). An unrecognised source is treated as drafted. The engine refuses a variant of yours with `source = "measured"` or none (only `measure` writes measured numbers), and says to use estimated or drafted. Demo mode ships four files in `demo/recipes/` (an estimated one, another estimated, a drafted one, a broken one with several errors); `scripts/dev recipe HOST [PATH]` opens the card with a path typed in.

## Remove

`startdgx delete` stops the model if it runs and deletes its weights at once, so the card is the question: it first asks the machine what that frees (`delete HOST MODEL --dry-run --json`, read-only) and says so (`removeConfirm`: "freeing 47.5 GiB that no other model uses", or that the weights are shared and nothing is freed). For a download in progress it is *Cancel the setup…*, which deletes what was downloaded so far. The **Remove** pill (danger) and `y` wait for that answer (Enter does nothing there); if the machine can't give it, the card says why in red and the removal can still go ahead. **Keep it**, Esc or a click outside close it and nothing happens. The removal runs with a 600 s timeout, since it returns only once the model is gone.

## Forget

A machine's **Forget…** (`f`) asks in a card: it takes the machine off this list, nothing on the machine changes, and Add machine can add it again. **Forget** (danger) or Enter forgets it; **Keep it**, Esc or a click outside close it.

## Uninstall

`startdgx launch uninstall` runs the real uninstall at once, so the card is the confirmation: it first shows the plan (`startdgx uninstall HOST --dry-run --json`, which changes nothing), and its **Uninstall…** pill (danger, enabled only once the plan for the chosen opt-ins has been read) opens the terminal that does it. Opt-ins, off by default and shown only where they would do something (`DgxModel.uninstallChoices`), say what they cost: **Also delete the recipes you added** (`--delete-recipes`; your recipes live in the engine's state dir, which uninstall otherwise deletes, so they are kept unless this is on, and the install manifest never records them), **Also delete the model weights** (`--delete-models`, with the space it frees) and **Also remove the packages the install added** (`--remove-packages`, naming them; anything else that uses them stops working, python3 always stays). Each change asks for the plan again; a removal apt would widen fails there and keeps the pill off. **Cancel**, Esc or a click outside close it and nothing happens.

## Terminals

Install, uninstall and logs need a person at a terminal, so they run in Omarchy's floating terminal through `startdgx launch`, started detached, and the window closes to get out of the way. `startdgx launch author HOST REPO` is the same path for a Find result's **With an agent…**: the terminal runs `recipe author --agent --here`, drafts the recipe and starts the configured agent in it. Nothing comes back to the manager: the terminal shows the result (Omarchy's Done/Failed prompt), and in demo mode, where the launch only prints what it would run, nothing is shown at all.

## Words

- A **machine** is a DGX Spark added to startdgx (its SSH target); a **model** is one of the engine's recipes set up on it.
- A **user recipe** is one you added from a `.toml` of your own (marked *yours*); a **curated recipe** ships with the engine. A **variant** is one context size of a recipe with its memory, and its **source** (measured, estimated or drafted) says where those numbers come from.
- **Find** is the Find on Hugging Face card: a search of Hugging Face from this computer. A **draft** is a user recipe startdgx writes for one of its results (`recipe draft`): the pinned commit, license and one drafted variant with placeholder numbers, which are never a fit until a measuring run. **Draft recipe** writes and adds one; **With an agent…** hands it to an agent.
- *Add* puts a machine that already runs the engine on the list; *Install…* sets the engine up on one; *Uninstall…* takes it off again; *Forget…* only takes the machine off this list, after a question.

## The bar icon

A server glyph at the end of the right section: dim when nothing runs, accent while a model runs or moves, red when a machine doesn't answer or a model failed. Left click opens or closes the manager, right click looks again. It reads one word (`idle`, `running`, `busy`, `alert`, from `DgxModel.summarize`) from `~/.cache/startdgx/status`, which the service rewrites whenever it changes.

## Notifications

A model that fails, or a setup that does, is a critical notification, once per failure and again if it comes back with another reason (`DgxModel.alerts`); not while the manager is open.

## Shared UI code
